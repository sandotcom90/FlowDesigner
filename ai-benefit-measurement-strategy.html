Measuring what AI tools actually gave the business

Tool adoption is already tracked and tells us little. This note sets out how to measure realised benefit at the user and business level, and how to keep experiments out of the numbers.

Activity ≠ Output ≠ Benefit

A proof-of-concept pull request is activity. A merged pull request is output. Neither is a benefit until something changed for the business. Every method below exists to hold that distinction.

01Filtering

Put a value gate in front of everything

Nothing counts as a benefit until it passes a gate. Define the stages, and only measure benefit past the last one.

Value gate — where a piece of AI work stops

Attempted
Produced
Accepted
In production
Business‑affecting
Does not enter the benefit calculation Counts as benefit

A proof-of-concept pull request stops at Produced. It enters neither the numerator nor the denominator of the benefit calculation. This one rule removes most of the noise in the current portfolio, and it holds up when challenged.

Two consequences worth designing for

  • Measure experiments separately, on different metrics. Proofs of concept aren't waste — they buy options. Judge that portfolio on conversion rate to production and cost per experiment, not on savings. That supports an honest and quite strong statement: we spent £X on 200 experiments, 12 converted, and those 12 produced £Y.
  • Track the failure cost. Effort spent on AI attempts that were discarded is a real cost and belongs in the denominator. Leaving it out inflates the return by ignoring the misses.
02Capture

Instrument the work item, not the tool

Add a small set of fields to the systems where work is already tracked — Jira, ServiceNow, the change and release system.

FieldCaptures
ai_assistedYes / no.
ai_toolWhich tool was used.
ai_roleDrafted, accelerated, reviewed, or fully autonomous. This matters a great deal — drafted then heavily rewritten is a different benefit from merged as-is.
effort_actualPerson-hours at closure.
effort_counterfactualHow long this would have taken without the tool.

The last field is the crux. It is self-reported, but asked at the moment of completion about a specific item it is far more reliable than a quarterly "how much time did AI save you." The result is paired data — actual against counterfactual, per work item and per task type — so the output is a distribution rather than a single hopeful number.

Make it two clicks, not a form. If closing a ticket takes an extra 90 seconds, compliance dies.

03Baseline

Build a task archetype catalogue

The most credible number available is per task type, not per tool. Identify the 10–20 recurring archetypes in the estate, for example:

  • Write unit tests for an existing module
  • Convert a stored procedure to Spark or PySpark
  • Produce an interface specification document
  • Triage a production incident to root cause
  • Build a regulatory report extract
  • Update dependencies and fix the breakages
  • Summarise a 60-page requirements document

For each, establish a baseline effort from historical tickets or a small timed sample, then measure the same archetype with AI assistance. That yields a per-archetype multiplier: test authoring runs 2.1× faster, stored procedure conversion 1.3×, incident triage no measurable change.

Why this holds up

  • It survives scrutiny far better than a blended average.
  • It shows management where to push adoption next.
  • It extrapolates: archetype volume × multiplier × rate = benefit, computed from work volumes already on hand.
04Passive signal

Estimate-vs-actual drift

Historical estimates already sit in Jira. Compare the ratio of estimated to actual effort for AI-assisted against non-assisted work of the same type and size. Estimates were set by people using pre-AI intuition, so a systematic overshoot on AI-assisted items is a genuine signal — and it costs nothing to collect, because the data already exists.

Watch the obvious confound: once people know the tools are available, they start estimating lower and the signal decays. This works best in the first few months after a rollout.

05Business level

Measure the business process, not the IT activity

For anything user-facing, the benefit shows up in a process metric owned by a business person, not by the delivery team.

  • Cases or transactions closed per FTE per period
  • Average handling time and touch time per case
  • End-to-end cycle time from request to fulfilment
  • Rework rate, error rate, first-time-right percentage
  • Backlog age and its distribution
  • Deflection — queries resolved without a human touch, and satisfaction on those
  • Unit cost — per report produced, per case handled, per release shipped

"Cost per regulatory report fell from $4,100 to $2,800" is a far more powerful sentence than "we saved 3,000 hours."

Handling attribution

  • Intervention log. Keep a dated record of everything that changed for that process — AI tooling, headcount, process redesign, system upgrades, volume shifts. When a metric moves, the candidate causes can at least be enumerated rather than guessed at.
  • Staggered enablement. Turn the tool on for one team, region, or product line before another and compare during the gap. It is the only inexpensive route to near-causal evidence, and it usually costs nothing because rollouts are staged anyway.
06User level

Ask users the right question, at the right moment

Replace periodic recall surveys with experience sampling: a single question at task closure, or on a randomly sampled 5% of completed items.

AskWhy it works
Duration"How long did this take you?" — compared against the archetype baseline. No AI framing at all, so no priming bias.
Counterfactual"Without the tool this would have taken: same / 25% longer / 50% longer / 2× / I wouldn't have attempted it."
Disposition"What did you do with the time freed?" — took on additional work / reduced overtime / deeper quality work / no change.

That last question is what converts hours into a claim finance will recognise, and it is the one almost nobody asks.

Alongside it, run a small number of timed paired trials — 15 to 20 people, one realistic task from the archetype catalogue, half with the tool. A single well-run trial produces a hard multiplier that anchors all the self-reported data around it. It takes a few days and is disproportionately valuable the moment someone challenges the numbers.

07Undercount risk

Capture the benefits that aren't time savings

Some of the real value never appears in an hours-saved column. Ignoring these undercounts badly.

BenefitHow to measure it
New workAnalysis, test coverage, documentation and refactoring that was previously never prioritised. Count the volume of newly attempted work and describe its value, rather than forcing it into a time saving.
QualityDefect escape rate, incidents, audit findings, rework percentage — converted using existing cost-per-defect or cost-per-incident figures where they exist.
Speed to marketDays earlier a capability landed × the daily value of that capability. Only usable where the business will state the daily value.
Key-person riskTime for a new joiner to first productive commit; dependency on single experts for legacy platforms. Very real where PeopleSoft and Essbase-era systems are still load-bearing.
Absorbed growthVolume grew X% while headcount stayed flat — often the cleanest cost-avoidance story available.
08Discipline

Attribution discipline

Two tests to apply before any claim enters the benefits register.

The counterfactual test

Would this have been done anyway, by other means, and at what cost?

If the answer is "yes, manually, in three days," the benefit is three days minus the AI effort. If the answer is "it would not have been done," the benefit is the value of a new capability, not a time saving. Different category — don't mix them.

The displacement test

Did the effort actually leave, or did it move?

Reviewing AI output, verifying summaries, correcting invented logic and clearing abandoned branches are all real hours. Net benefit = gross time saved − verification − rework − discarded attempts. Ask for the net.

Being visibly the person who insists on the net figure is what makes every other number in the pack believable.

Recommendation

The shortest defensible path to a real number

The full framework doesn't need to land at once. Four moves produce an auditable figure within a quarter, and the method scales to the rest of the portfolio without being rebuilt.

  1. Pick three high-volume task archetypes and establish their baselines properly.
  2. Run one timed paired trial on each.
  3. Add the two closure fields to Jira — for those work types only.
  4. Put the value gate in front of everything.

That is enough to answer the question management is actually asking, with evidence that survives being challenged.
